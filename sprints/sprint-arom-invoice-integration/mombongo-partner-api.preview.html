Mombongo Partner API (1.1.1)

Download OpenAPI specification:

API surface for external partners integrating with Mombongo's payment and marketplace rails. AROM is the first (and currently only) partner.

Two invoice origins

  • Partner-originated (Sprint AI, live since 2026-08): your system creates an invoice via createExternalInvoice, then a Mombongo user pays it via createExternalInvoiceCheckout. This is what you already integrated.
  • Harvest-sale, partner-sourced (Sprint DP, new): a farmer publishes a harvest listing on Mombongo; you discover it via getExternalPublishedListings and submit an offer via createExternalHarvestOffer. If the farmer picks your offer, Mombongo creates the invoice itself and sends you the new invoiceIssued webhook. You then pay it the exact same way — createExternalInvoiceCheckout is unmodified and works identically regardless of which flow created the invoice.

Environment

There is a single Firebase project (mombongo-dev) — no separate staging/production project. Every partners and external_invoices document carries a testMode boolean; a new invoice inherits your partner account's testMode setting, so your sandbox and live traffic are distinguished by that flag, not by a different base URL or set of credentials.

Authenticating inbound requests (you → Mombongo)

Every endpoint below requires two headers:

  • x-partner-id — your partner id (e.g. arom).

  • x-partner-signature — lowercase hex HMAC-SHA256 of the raw request body bytes, using the hmacSecret we gave you when provisioning your account. Sign the bytes exactly as sent — not a re-serialized or re-ordered version of the JSON, since that can produce a different byte sequence than what we verify against.

    signature = hex(HMAC_SHA256(hmacSecret, rawRequestBodyBytes))

A missing header, an inactive partner account, or a signature mismatch all fail the same way: 401 Invalid signature. There is no partial credit or descriptive error here by design — we don't want to help an attacker narrow down which part of a forged request is wrong.

Authenticating outbound webhooks (Mombongo → you)

Both webhooks below are signed the same way, but with a different secret (outboundHmacSecret, not hmacSecret) and over the JSON-serialized payload (not raw bytes, since we're the ones constructing the request):

x-mombongo-signature = hex(HMAC_SHA256(outboundHmacSecret, JSON.stringify(payload)))

Verify this before trusting the payload. If your endpoint doesn't return a 2xx response, we retry up to 3 times with exponential backoff (2s, 4s), then give up — the event is logged on our side as a dead letter, visible to us in our own admin console with a manual-retry button, so if you were down when we tried, tell us and we can resend it by hand rather than you needing to reconcile from a polling loop.

Both outbound webhooks land on the same webhookUrl — every payload carries an event field ("payment_complete" or "invoice_issued") so your receiver can route without guessing from which other fields happen to be present.

Worked example — signing a request

A full, verifiable example for createExternalHarvestOffer, so you can check your own implementation produces the exact same signature for the exact same input before pointing it at a real secret.

Given hmacSecret = "test_hmac_secret_do_not_use_in_production" and this exact raw request body (note: no extra whitespace — sign the bytes you actually send, not a pretty-printed version):

{"listingId":"listing_abc123","offerQuantityKg":500,"offerPricePerKgCdf":450}

echo -n '{"listingId":"listing_abc123","offerQuantityKg":500,"offerPricePerKgCdf":450}' \
  | openssl dgst -sha256 -hmac "test_hmac_secret_do_not_use_in_production"

produces:

02abf6e9259aec73dcb388cc9e3d35d10075a5f9ca47d6351efa9d1f810f6c60

So the full request is:

curl -X POST https://europe-west1-mombongo-dev.cloudfunctions.net/createExternalHarvestOffer \
  -H "content-type: application/json" \
  -H "x-partner-id: arom" \
  -H "x-partner-signature: 02abf6e9259aec73dcb388cc9e3d35d10075a5f9ca47d6351efa9d1f810f6c60" \
  -d '{"listingId":"listing_abc123","offerQuantityKg":500,"offerPricePerKgCdf":450}'

If your computed signature doesn't match ours for this exact input, the mismatch is almost always in how the body gets serialized before signing — a JSON library that reorders keys, adds whitespace, or changes number formatting will produce a different byte sequence and therefore a different signature, even though the parsed JSON is "the same." Sign the literal bytes you're about to send on the wire.

Idempotency

createExternalInvoice is idempotent on externalInvoiceId — calling it twice with the same id returns { "status": "duplicate_ignored" } and the original invoice, rather than creating a second one. There is no equivalent idempotency key on createExternalHarvestOffer — each call creates a new offer, since a legitimate use case (offering twice at different prices) looks identical to an accidental retry from our side of that boundary.

Error responses

Most error responses are a plain-text body with a plain HTTP status code, not a JSON envelope — this mirrors this codebase's existing webhook conventions rather than introducing a new one just for this API. A few success/conflict responses that carry data are JSON (called out per-endpoint below). Don't assume every non-2xx body is parseable JSON.
